# Missing eBay conversations and offers from another buyer

## Findings

The code contains several independent paths that can produce the reported symptoms. These findings come from code inspection and regression tests; no live eBay account or production database was queried.

1. **Failed imports became permanently older than the sync cutoff.** `EbaySyncService._finalize_sync` advanced `last_sync_at` even after conversation failures or a capped import. `_iter_conversation_summaries` then skipped older summaries without checking whether they had actually been stored. It also stopped scanning after an entirely old page, so missing conversations on later pages could never be discovered. The creation date fallback was unsafe for conversations whose latest-message date was absent.
2. **Only the first 50 messages were imported.** The detail endpoint was called once with `offset=0`. Long conversations lost the remaining messages. eBay documents paginated responses with `total`, `next`, `limit`, and `offset`: [getConversation](https://www.developer.ebay.com/develop/api/commerce/message_api/conversation/getConversation).
3. **An offer failure could roll back message imports.** `EbayConversationOfferResolver` called `Session.rollback()` on offer insert/parse failures. That rolls back the outer transaction, including pending conversation/message inserts; the conversation savepoint did not protect against an explicit full rollback. Product enrichment also ran inside the message import savepoint, so its failure discarded the messages.
4. **An offer could be linked to the wrong buyer.** `EbayBestOfferSyncService._match_conversation` tried a buyer match, then fell back to the only conversation for the listing. For an offer by buyer 1 and a sole chat with buyer 2, that fallback returned buyer 2's conversation.
5. **Buyer and notification detection added confusion.** Buyer detection used a case-sensitive comparison with the seller username and could select `ebay` as the buyer. Offer parsing also included the conversation title for every message, allowing an older offer title to classify ordinary follow-up chat as another offer.

The conversation table has a unique key on `(provider, provider_conversation_id)`; messages have one on `(provider, provider_message_id)`. There is no conversation uniqueness constraint on item/listing ID. Two buyers asking about the same item can therefore have separate conversations. Existing provider-ID keys remain unchanged. Actual constraint failures should be identified through `SyncLog.sync_metadata.failed_conversations`, which includes provider conversation IDs and error text, before changing the schema.

The subsequent production logs show two additional observations: every time-filtered `FROM_MEMBERS` request returned zero summaries, and overlapping imports encountered `uq_conversations_provider_external_id` for notification conversation `210938288459`. The empty lists occur before any member-message persistence; they do not establish that eBay has no new replies. The logs also contain a separate duplicate order-line error. No quota rejection is visible in this excerpt.

## Implemented behavior

- For buyer/seller conversations, list summaries without provider `start_time`, then apply `last successful account sync - 1 minute` to latest-message activity locally. At 11:55 after an 11:50 successful sync, fetch details for activity from 11:49 onward, including the boundary. Routine runs stop after an entire page has known latest-message activity older than that cutoff, restoring the former small-call behavior. Unknown dates and boundary activity prevent the stop. Initial imports and periodic reconciliation runs paginate the full list. This avoids relying on provider time-filter behavior that returned empty member lists in production.
- eBay documents time filters only for `FROM_MEMBERS`. For `FROM_EBAY` system notifications, scan summaries on a separate configurable cadence, default 60 minutes per account. Intervening manual and scheduled syncs make zero notification list calls. A due notification scan applies its own previous successful notification cutoff minus one minute, rather than the newer member-sync cutoff, so notifications between scans stay eligible. No ordering assumption is used to skip unseen pages. See [eBay's Message API reference](https://www.ebay.co.jp/developer/api/message_api/documentation).
- Fetch every detail page before saving; reject incomplete pages and messages missing IDs so the conversation stays retryable.
- Advance the account cutoff to the sync start time only after an uncapped run without failed conversation imports or enrichment. Failure retains the previous cutoff so the next scheduled sync retries that window. Each account uses its own successful-sync timestamp.
- Isolate product enrichment and offer resolution with savepoints. Imported messages survive enrichment failures, and conversations with failed enrichment remain eligible for another attempt.
- Require account, listing, and buyer identity when linking best offers. Offers without a matching buyer remain stored without a conversation link. Replay detaches existing links to a different buyer/listing and clears their stale message links. Terminal offers also have their links corrected when re-observed.
- Compare usernames without case differences, exclude seller/eBay identities from buyer detection, and detect offer events from each message's subject/body.
- Reconcile concurrent PostgreSQL conversation inserts using `ON CONFLICT DO NOTHING`, then reload and update the existing conversation. The unique provider identity remains enforced without discarding the imported messages on an insert race.
- Log account ID, effective cutoff, HTTP status, and whether the notification scan is due. An empty member list directs diagnosis toward the account/provider response.

## Recovery after deployment

An account without a previous successful sync performs its initial full import. Subsequent manual and scheduled runs use the one-minute-overlap window. Changing the schedule to five minutes changes when a run occurs; it does not change the one-minute overlap.

The first notification run after deployment establishes its separate cursor using the existing account cutoff (or all history for a never-synced account). Later successful notification runs record `notification_sync.synced_through` in sync metadata. Member-only runs, failures, enrichment failures, and capped runs cannot advance that cursor. Configure `api.ebay_notification_sync_interval_minutes` in settings; the backend uses 60 even before the settings row is created. System notifications can arrive in this app up to one notification interval plus scheduler/run time later than on eBay. Buyer/seller chats keep the regular schedule.

The same extended run reconciles member summaries using the saved extended-scan cutoff. This older window is essential: recent routine member runs may have advanced the account cutoff despite stopping before a later-page update. Because ordering by latest activity is not guaranteed, an update behind an old page can appear only at reconciliation time, up to the extended interval plus scheduler/run time later. The saved cursor advances only after the whole uncapped conversation scan succeeds.

For 7,309 notifications and 50 summaries per page, each due scan still requires 147 list requests. At a three-minute member interval, the hourly cadence reduces notification listing from about 2,940 to 147 calls per hour per account (95% fewer). Quiet routine runs generally need one member summary page per account, plus existing order/offer calls. Roughly 15 calls per five minutes is a workload estimate, not a hard limit or a guaranteed average: new messages, long threads, retries, initial imports, and extended scans require more. Extended runs retain full pagination to compensate for the routine old-page stopping assumption.

Historical gaps predating the selected window require an explicit backfill; routine incremental sync does not automatically rescan history. Existing completion markers are no longer used to decide which conversations to fetch. Inspect `updated_since`, `failed_conversations`, and `enrichment_failed_conversation_ids` in sync metadata for the effective window and unresolved failures. No database migration is required.

The member-list change removes the suspected provider-filter exclusion, but no live account was queried to prove the production cause. After deployment, compare a known new message's conversation ID and latest-message time with the unfiltered member summaries and detail response if it still does not appear. Historical gaps older than the retained cutoff still require explicit backfill.

This recovery cannot import conversations eBay does not return, and does not split or delete messages inside a conversation supplied as mixed by eBay itself. If a specific conversation is still missing after recovery, compare its eBay conversation ID and raw provider response with the sync log. The changes do not establish that every reported production example had the same cause.
